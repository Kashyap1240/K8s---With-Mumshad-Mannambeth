## 1. Why Manual Scheduling? 🤔

What if your cluster has **no scheduler**, or you don't want to rely on the built-in one and want to place pods yourself? To do that, you first need to know how the scheduler works behind the scenes.

## 2. How the Scheduler Works ⚙️

Every pod has a field called **`nodeName`**.

- By default it is **not set**. You don't normally write it in the manifest; Kubernetes adds it automatically.

The scheduler's job:

1. Goes through all pods and looks for those **without `nodeName`**. These are the candidates for scheduling.
2. Runs the **scheduling algorithm** to find the right node.
3. Schedules the pod by setting `nodeName` to the chosen node, **by creating a Binding object**.

```
Pod (no nodeName) ──► Scheduler picks a node ──► Binding object ──► nodeName = node02
```

## 3. No Scheduler = Pending Pods ⏳

If nothing monitors and schedules pods, they stay in the **`Pending`** state forever.

```bash
kubectl get po
# NAME    READY   STATUS    NODE
# nginx   0/1     Pending   <none>
```

## 4. Manually Assigning a Pod to a Node 🛠️

### Method 1: set `nodeName` at creation time (easiest)

Put the node's name in the pod spec **while creating the pod**:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    name: nginx
spec:
  nodeName: node02
  containers:
    - name: nginx
      image: nginx
```

The pod is assigned straight to `node02`.

⚠️ You can **only** set `nodeName` at **creation time**.

### Method 2: Binding object (for a pod that already exists)

Kubernetes **won't let you modify** `nodeName` on an existing pod. Instead, **mimic what the scheduler does**:

1. Create a **Binding** object with the target node.
2. Send a **POST request** to the pod's **binding API**, with the Binding in **JSON** format (so convert the YAML to JSON).

Binding definition (YAML form):

```yaml
apiVersion: v1
kind: Binding
metadata:
  name: nginx
target:
  apiVersion: v1
  kind: Node
  name: node02
```

POST request with the JSON equivalent:

```bash
curl --header "Content-Type:application/json" \
  --request POST \
  --data '{"apiVersion":"v1","kind":"Binding","metadata":{"name":"nginx"},"target":{"apiVersion":"v1","kind":"Node","name":"node02"}}' \
  http://$SERVER/api/v1/namespaces/default/pods/nginx/binding/
```

## 5. Quick Comparison 📊

| Method                | When to use                      | Notes                                                       |
|-----------------------|----------------------------------|-------------------------------------------------------------|
| `nodeName` in YAML    | Creating a **new** pod           | Simplest option; only works at creation time                |
| Binding object + POST | Pod **already exists**           | Mimics the scheduler; needs JSON and a call to the API server |

💡 **Extra tip (not from the lecture):** an easier way to move an existing pod is often to **delete and recreate** it with `nodeName` set, e.g. edit the YAML and run `kubectl replace --force -f pod.yaml`. Check where a pod landed with `kubectl get po -o wide`.

## 🚀 Summary Cheat Sheet

| Concept / Command                    | Purpose                                                       |
|--------------------------------------|---------------------------------------------------------------|
| `spec.nodeName`                      | Field that records which node the pod runs on                 |
| Binding object                       | How the scheduler sets `nodeName` on a pod                    |
| `kubectl get po -o wide`             | See which node each pod is on                                 |

- Pods with **no `nodeName`** are the scheduler's candidates.
- Scheduler = find pods without `nodeName` → run algorithm → create **Binding** → `nodeName` set.
- **No scheduler → pods stay `Pending`.**
- Manual scheduling: set `nodeName` **at creation time**.
- Existing pod: `nodeName` can't be edited, so create a **Binding** and **POST** it (JSON) to `/pods/<name>/binding`.
