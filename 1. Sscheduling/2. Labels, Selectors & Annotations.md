## 1. What Are Labels and Selectors? 🏷️

Labels and selectors are a **standard method to group things together** and filter them.

Analogy: a set of animals. You want to filter them by:

- **class / kind** (mammal, bird)
- **domestic or wild**
- **color**
- or **multiple criteria**, like "everything green that is also a bird"

| Term         | Meaning                                                  | Example                     |
|--------------|----------------------------------------------------------|-----------------------------|
| **Label**    | A property **attached to each item**                     | `class: mammal`, `color: green` |
| **Selector** | A condition used to **filter** items by their labels     | `class = mammal` → all mammals; `color = green` → green mammals |

You see this everywhere: tags on YouTube videos and blogs, or filters in an online store.

## 2. Why Do We Need Them in Kubernetes? 🤔

- A cluster can end up with **hundreds or thousands** of objects: pods, services, ReplicaSets, deployments, etc.
- You need a way to **filter and view** them by category: by type, by application, by functionality, and so on.
- Attach labels as needed (`app`, `function`, ...), then use a selector with a condition to pick specific objects, e.g. `app = App1`.

## 3. Specifying Labels ✍️

In a Pod definition, add a `labels` section under `metadata` as **key-value pairs**. You can add as many as you like.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: simple-webapp
  labels:
    app: App1
    function: Front-end
spec:
  containers:
    - name: simple-webapp
      image: simple-webapp
      ports:
        - containerPort: 8080
```

### Selecting objects with a selector

```bash
kubectl get pods --selector app=App1

# short form
kubectl get po -l app=App1

# multiple conditions
kubectl get po -l app=App1,function=Front-end
```

💡 **Extra tip (not from the lecture):** `kubectl get po --show-labels` displays the labels of each pod.

## 4. How Kubernetes Uses Labels Internally 🔗

Kubernetes objects use labels and selectors to **connect to each other**.

### ReplicaSet → Pods

1. **Label** the pod definition (inside the `template`).
2. Use a **selector** in the ReplicaSet to group those pods.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: simple-webapp
  labels:                 # labels of the ReplicaSet itself
    app: App1
    function: Front-end
spec:
  replicas: 3
  selector:
    matchLabels:
      app: App1           # must match the POD labels
  template:
    metadata:
      labels:             # labels on the PODS
        app: App1
        function: Front-end
    spec:
      containers:
        - name: simple-webapp
          image: simple-webapp
```

### ⚠️ Common beginner mistake: labels appear in two places

| Location in the file               | Labels belong to      | Purpose                                                       |
|------------------------------------|-----------------------|---------------------------------------------------------------|
| Top `metadata.labels`              | The **ReplicaSet** itself | Only used if another object needs to discover the ReplicaSet |
| `template.metadata.labels`         | The **pods**          | What the ReplicaSet's selector matches against                |

- The `selector` under `spec` must **match the labels on the pods** (the template labels).
- **One label is enough** if it matches correctly.
- If other pods might share that label but have a different function, specify **multiple labels** so the right pods are discovered.
- If the labels match, the ReplicaSet is created successfully.

### Service → Pods

It works the same way. A Service uses the `selector` in its definition to match the **labels set on the pods** (the ones from the ReplicaSet's template):

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: App1
  ports:
    - port: 80
      targetPort: 8080
```

## 5. Annotations 📝

|                | Labels & Selectors                          | Annotations                                            |
|----------------|---------------------------------------------|--------------------------------------------------------|
| **Purpose**    | **Group and select** objects                | Record **other details for information**              |
| **Used for**   | Filtering, connecting objects               | Tool details (name, version, build info), contact details (phone numbers, email IDs) for integrations |

```yaml
metadata:
  name: simple-webapp
  labels:
    app: App1
  annotations:
    buildversion: "1.34"
```

## 🚀 Summary Cheat Sheet

| Command / Concept                         | Purpose                                      |
|-------------------------------------------|----------------------------------------------|
| `kubectl get po --selector app=App1`      | Filter pods by label                         |
| `kubectl get po -l app=App1,function=Front-end` | Filter with multiple labels            |
| `metadata.labels`                         | Attach labels to an object                   |
| `spec.selector` (+ `matchLabels`)         | Select which objects to manage / route to    |
| `metadata.annotations`                    | Store informational details                  |

- **Labels** = properties on objects. **Selectors** = filters on those labels.
- Kubernetes objects connect through them: **ReplicaSet → pods** and **Service → pods**.
- In a ReplicaSet, the selector must match the **`template` labels** (the pod labels), not the ReplicaSet's own labels.
- Use **multiple labels** to avoid picking up unrelated pods.
- **Annotations** are for info only (build version, contact details), not for selecting.
