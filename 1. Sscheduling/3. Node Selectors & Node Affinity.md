## 1. The Problem 🤔

Example: a **3-node cluster**.

| Node   | Size                                  |
|--------|---------------------------------------|
| Node 1 | **Large** (higher hardware resources) |
| Node 2 | Small (lower resources)               |
| Node 3 | Small (lower resources)               |

- You want **data processing workloads** (which need more horsepower) to run on the **large node**, the only one that won't run out of resources if the job needs extra.
- By default, **any pod can go to any node**, so the data processing pod might end up on node 2 or 3. ❌

📌 Solution: **limit the pod so it only runs on particular nodes.** There are two ways:

1. **Node selectors**: simple and easy
2. **Node affinity**: advanced and more powerful

---

## 2. Node Selectors 🏷️

### How they work ⚙️

Add a `nodeSelector` property to the `spec` section of the pod, using a key-value pair:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: data-processor
spec:
  containers:
    - name: data-processor
      image: data-processor
  nodeSelector:
    size: large
```

**Where does `size: large` come from?** These are **labels assigned to the nodes**. The scheduler matches the pod's `nodeSelector` against node labels to find the right node.

⚠️ You must **label the nodes first**, *before* creating the pod.

### Labelling a node

```bash
kubectl label nodes <node-name> <label-key>=<label-value>

# Example
kubectl label nodes node01 size=large

# Then create the pod
kubectl create -f pod-definition.yaml
```

✅ The pod is now placed on **node 1** as desired.

💡 **Extra tip (not from the lecture):** check node labels with `kubectl get nodes --show-labels`.

### Limitations 🚧

Node selectors use a **single label and selector**. That fails for more complex needs, such as:

- "Place the pod on a **large OR medium** node"
- "Place the pod on any node that is **NOT small**"

❌ These **can't** be expressed with node selectors. That's why **node affinity and anti-affinity** were introduced.

## 3. Node Affinity 🎯

### What is it?

- Primary purpose: **ensure pods are hosted on particular nodes**, e.g. make sure the large data-processing pod ends up on the large node.
- Gives **advanced capabilities** to limit pod placement, including expressions like `OR` and `NOT` that node selectors can't do.

> "With great power comes great complexity."

### Syntax

Same result as the `nodeSelector` above, but a longer definition:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: data-processor
spec:
  containers:
    - name: data-processor
      image: data-processor
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: size
                operator: In
                values:
                  - large
```

| Part                                              | Meaning                                                      |
|---------------------------------------------------|--------------------------------------------------------------|
| `spec.affinity.nodeAffinity`                      | Where node affinity rules live                               |
| `requiredDuringSchedulingIgnoredDuringExecution`  | The **type** of node affinity (the long "sentence" property) |
| `nodeSelectorTerms`                               | An **array** where you specify the rules                     |
| `matchExpressions` → `key`, `operator`, `values`  | Each rule is in the form **key operator value**              |

### Operators 🔧

| Operator   | Meaning                                                                    | Example                                          |
|------------|----------------------------------------------------------------------------|--------------------------------------------------|
| `In`       | Node label's value is **any of the listed values**                         | `size In [large, medium]` → large **or** medium  |
| `NotIn`    | Node label's value is **not** any of the listed values                     | `size NotIn [small]` → any node not small        |
| `Exists`   | Node **has the label**, whatever its value. **No `values` section needed** | `size Exists` → nodes where `size` is set        |

```yaml
# Large OR medium
- key: size
  operator: In
  values:
    - large
    - medium
```

```yaml
# Anything that is NOT small
- key: size
  operator: NotIn
  values:
    - small
```

```yaml
# Label exists (no values needed)
- key: size
  operator: Exists
```

💡 Why `NotIn` and `Exists` work here: only the large and medium nodes have the `size` label. The small nodes **don't have it set at all**, so these checks give the same result, as long as you don't label the small nodes.

There are other operators too (check the Kubernetes docs for details).

### Types of node affinity 🧬

The **type** defines the scheduler's behaviour at two stages in the pod's lifecycle:

- **During scheduling**: the pod doesn't exist yet and is created for the first time.
- **During execution**: the pod is already running and something changes (e.g. a node's label is changed).

| Type                                                | During scheduling | During execution |
|-----------------------------------------------------|-------------------|------------------|
| `requiredDuringSchedulingIgnoredDuringExecution`    | **Required**      | Ignored          |
| `preferredDuringSchedulingIgnoredDuringExecution`   | **Preferred**     | Ignored          |
| `requiredDuringSchedulingRequiredDuringExecution`   | Required          | Required         |

🚧 The first two are **available now**. The third is **planned** and not available as of the lecture.

#### During scheduling: required vs preferred

What if no node matches (e.g. you forgot to label the node `large`)?

| Type          | Behaviour when no matching node is found                                                   | Use when                                             |
|---------------|--------------------------------------------------------------------------------------------|------------------------------------------------------|
| **Required**  | The scheduler **mandates** a matching node. If none is found, the pod is **not scheduled** | Pod placement is **crucial**                         |
| **Preferred** | The scheduler **ignores the affinity rules** and places the pod on **any available node**  | Running the workload matters more than where it runs |

Preferred = "try your best to place the pod on a matching node, but if you can't, just place it anywhere."

#### During execution: Ignored

What if an admin **removes the label** (e.g. `size=large`) from a node while pods are running on it?

- Both available types are **`IgnoredDuringExecution`**.
- Pods **keep running**. Changes to node labels **don't affect them** once they are scheduled.

### Extra: `preferred` syntax 💡

*(Not shown in the lecture, added for reference.)* The preferred type uses a `weight` and a `preference`:

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
            - key: size
              operator: In
              values:
                - large
```

## 4. Node Selector vs Node Affinity ⚖️

| Feature                    | `nodeSelector`                  | `nodeAffinity`                                           |
|----------------------------|---------------------------------|----------------------------------------------------------|
| Complexity                 | Simple, easy                    | Longer, more complex                                     |
| Matching                   | Single label, exact match       | Expressions: `In`, `NotIn`, `Exists`, and more           |
| `OR` / `NOT` conditions    | ❌ Not possible                 | ✅ Supported                                             |
| If no node matches         | Pod isn't scheduled             | **Required** → not scheduled, **Preferred** → any node  |
| Running pods if label changes | Not affected                 | Not affected (`IgnoredDuringExecution`)                  |

## 🚀 Summary Cheat Sheet

| Command / Concept                                  | Purpose                                                     |
|----------------------------------------------------|-------------------------------------------------------------|
| `kubectl label nodes <node> <key>=<value>`         | Label a node                                                |
| `spec.nodeSelector`                                | Restrict a pod to nodes with a matching label               |
| `spec.affinity.nodeAffinity`                       | Advanced placement rules (`In`, `NotIn`, `Exists`, ...)     |
| `requiredDuringSchedulingIgnoredDuringExecution`   | Must match at scheduling, else pod isn't scheduled; ignored later |
| `preferredDuringSchedulingIgnoredDuringExecution`  | Try to match; otherwise place anywhere; ignored later       |
| `requiredDuringSchedulingRequiredDuringExecution`  | **Planned**, not available yet                              |

- Node selector = **label the node first, then reference the label in the pod**. One label, simple match only.
- Node affinity = **node selector with advanced expressions** (`OR`, `NOT`, exists).
- Rule format: **key operator value** (no `values` for `Exists`).
- **Required** → pod stays unscheduled if no match. **Preferred** → falls back to any node.
- **IgnoredDuringExecution** → label changes don't affect running pods.
