## 1. Resource Requirements Basics 🧮

- Each node has a set of **CPU and memory** available.
- Each pod **requires** resources to run (e.g. 2 CPUs and 1 unit of memory).
- When a pod is placed on a node, it **consumes** that node's resources.

The **scheduler** decides which node a pod goes to:

1. Looks at what the pod **requires** and what each node has **available**.
2. Picks the **best node** with sufficient resources.
3. **Avoids** nodes without enough resources.
4. If **no node** has enough, it holds the pod back → the pod stays **`Pending`**.

```bash
kubectl describe pod <pod-name>
# Events: ... Insufficient cpu
```

---

## 2. Resource Requests 📥

- The **minimum** amount of CPU or memory a container asks for.
- The scheduler uses these numbers to find a node with enough free resources.
- Once placed, the pod gets a **guaranteed** amount of those resources.

Add a `resources` section with `requests` in the container spec:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: simple-webapp-color
  labels:
    name: simple-webapp-color
spec:
  containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      ports:
        - containerPort: 8080
      resources:
        requests:
          memory: "4Gi"
          cpu: 2
```

## 3. CPU and Memory Units 📏

### CPU

| Value   | Meaning                                    |
|---------|--------------------------------------------|
| `1`     | 1 CPU                                      |
| `0.1`   | Same as `100m` (`m` = **milli**)           |
| `1m`    | Lowest allowed value (can't go lower)      |
| `5`     | You can request more CPUs if nodes have enough |

**1 CPU** equals:

- **1 vCPU** on AWS
- **1 core** on GCP / Azure
- **1 hyperthread** on other systems

### Memory

| Suffix | Meaning                      | Equivalent                 |
|--------|------------------------------|----------------------------|
| `256Mi`| 256 **mebibytes**            | `268435456` (plain number of bytes) |
| `M`    | **megabyte** (1000-based)    | 1 M = 1,000,000 bytes      |
| `G`    | **gigabyte** (1000-based)    | 1 G = 1000 M               |
| `Gi`   | **gibibyte** (1024-based)    | 1 Gi = 1024 Mi             |

⚠️ **Note the difference:** `G` (gigabyte) = 1000 MB, whereas `Gi` (gibibyte) = 1024 MiB. The same applies to `M`/`Mi` and `K`/`Ki`.

## 4. Resource Limits 🚧

- By default a container has **no limit**, so it can consume as much as it wants on the node and **starve** native processes and other containers.
- Set **limits** to cap usage, under `limits` in the same `resources` section:

```yaml
resources:
  requests:
    memory: "1Gi"
    cpu: 1
  limits:
    memory: "2Gi"
    cpu: 2
```

- Requests and limits are set **per container** inside a pod. With multiple containers, each can have its own.

### What happens when a container exceeds its limit?

| Resource   | Behaviour                                                                                          |
|------------|----------------------------------------------------------------------------------------------------|
| **CPU**    | The system **throttles** the CPU. The container **cannot** use more than its limit                 |
| **Memory** | The container **can** use more than its limit, but if it keeps doing so the pod is **terminated** with an **OOM (Out Of Memory) kill**, visible in the logs or `kubectl describe` |

---

## 5. Request/Limit Scenarios: CPU ⚙️

By default Kubernetes has **no CPU or memory requests or limits** set, so any pod can consume as much as it needs on any node and starve others.

Scenarios with two pods competing for CPU:

| # | Setup                       | Result                                                                                                     |
|---|-----------------------------|------------------------------------------------------------------------------------------------------------|
| 1 | **No requests, no limits**  | One pod can consume **all** CPU on the node and starve the other ❌                                         |
| 2 | **Limits only**             | Kubernetes sets **requests = limits**. Each pod is guaranteed that amount and can't go beyond it           |
| 3 | **Requests and limits**     | Each pod is guaranteed its request (e.g. 1 vCPU) and can burst up to the limit (e.g. 3 vCPU). Downside: if pod 1 needs more while pod 2 is idle, it's still **capped** at the limit |
| 4 | **Requests only, no limits** ✅ | Each pod is **guaranteed** its request. When free, any pod can use extra CPU cycles. If another pod needs what it requested, it **gets it back** |

📌 Scenario 4 is considered the **most ideal** setup for CPU: guaranteed minimum, no unnecessary capping.

### When limits make sense

- Example: the public course labs run as containers on a shared cluster. Limits stop users from misusing resources (e.g. **Bitcoin mining**).
- If you don't want to restrict your application, **don't set limits**. But then make sure **every pod has requests set**. Otherwise a pod without requests can be starved by others that have none.
- Requests and limits can be **different per container**. The examples use the same values only for simplicity.

---

## 6. Request/Limit Scenarios: Memory 🧠

Same four scenarios, but **memory can't be throttled**:

| # | Setup                       | Result                                                                                         |
|---|-----------------------------|------------------------------------------------------------------------------------------------|
| 1 | No requests, no limits      | One pod can consume all memory and starve the other ❌                                          |
| 2 | Limits only                 | Requests = limits (e.g. 3 GB each); guaranteed and capped                                      |
| 3 | Requests and limits         | Guaranteed the request (e.g. 1 GB), can go up to the limit (e.g. 3 GB)                         |
| 4 | Requests only, no limits    | Guaranteed the request. Pods can use extra memory when free. If another pod needs memory back, the **only option is to kill the pod** |

📌 **Why kill?** Unlike CPU, once memory is assigned to a pod it **can't be throttled**. The only way to reclaim it is to **kill the pod** and free its memory.

## 7. LimitRange 📐

**Problem:** by default pods have no requests or limits. How do you make sure every pod gets sensible defaults?

**LimitRange** defines **default values** for containers created **without** a request or limit in their pod definition.

- It's a **namespace-level object**.
- Separate LimitRanges for CPU and memory (or both in one).

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-resource-constraint
spec:
  limits:
    - default:            # default LIMIT
        cpu: 500m
      defaultRequest:     # default REQUEST
        cpu: 500m
      max:                # max LIMIT a container can set
        cpu: "1"
      min:                # min REQUEST a container can make
        cpu: 100m
      type: Container
```

Memory works the same way:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: memory-resource-constraint
spec:
  limits:
    - default:
        memory: 1Gi
      defaultRequest:
        memory: 1Gi
      max:
        memory: 1Gi
      min:
        memory: 500Mi
      type: Container
```

| Field            | Meaning                                                      |
|------------------|--------------------------------------------------------------|
| `default`        | Limit applied if the container doesn't specify one           |
| `defaultRequest` | Request applied if the container doesn't specify one         |
| `max`            | **Maximum limit** a container can set                        |
| `min`            | **Minimum request** a container can make                     |

⚠️ These values are **examples**, not recommendations. Choose what's best for your applications.

⚠️ LimitRange is enforced **at pod creation**. Creating or changing one **does not affect existing pods**, only pods created afterwards.

## 8. ResourceQuota 🧾

**Problem:** how to restrict the **total** resources consumed by all applications in a namespace (e.g. all pods together shouldn't use more than X CPU or memory)?

**ResourceQuota** is a **namespace-level object** that sets **hard limits** on total requests and limits:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 4Gi
    limits.cpu: "10"
    limits.memory: 10Gi
```

This quota means that in the namespace:

- Total **requested CPU** ≤ 4, total **requested memory** ≤ 4 GB
- Total **CPU limits** ≤ 10, total **memory limits** ≤ 10 GB

### LimitRange vs ResourceQuota

| Feature           | LimitRange                                          | ResourceQuota                                      |
|-------------------|-----------------------------------------------------|----------------------------------------------------|
| Scope             | Namespace level                                     | Namespace level                                    |
| Applies to        | **Each container / pod** individually               | The **total** across all pods in the namespace     |
| Purpose           | Defaults, min and max per container                 | Hard cap on total requests and limits              |

## 🚀 Summary Cheat Sheet

| Concept / Command                  | Purpose                                                                 |
|------------------------------------|-------------------------------------------------------------------------|
| `resources.requests`               | **Minimum** guaranteed; used by the scheduler to pick a node            |
| `resources.limits`                 | **Maximum** a container can use                                         |
| `kubectl describe pod <name>`      | See events like `Insufficient cpu` or an OOM kill                       |
| `LimitRange`                       | Default / min / max requests and limits per container (namespace)       |
| `ResourceQuota`                    | Total requests and limits allowed in a namespace                        |

- **No resources specified** → no guarantees, any pod can starve others.
- **No node has enough** → pod stays **`Pending`** (`Insufficient cpu`).
- `100m` = 0.1 CPU; minimum is `1m`. 1 CPU = 1 vCPU / core / hyperthread.
- `G` = 1000 M, `Gi` = 1024 Mi. Don't mix them up.
- **CPU over limit** → **throttled**. **Memory over limit** → **OOM killed**.
- Only limits set → requests automatically equal limits.
- **Best practice for CPU:** set **requests, no limits** (and make sure *every* pod has requests).
- LimitRange only affects **new** pods.
- Requests and limits are set **per container**, not per pod.
