# 👹 DaemonSets: One Pod Per Node

## 1. What is a DaemonSet? 📝

- **Definition:** A workload controller that ensures **exactly one replica of a Pod runs on every Node** in the cluster.
- **vs ReplicaSet:** A ReplicaSet maintains *N* replicas placed anywhere the scheduler decides; a DaemonSet maintains **1 replica per node**, with no `replicas` field.
- **Auto-reconciliation:**
  - Node added → Pod automatically created on it.
  - Node removed → Pod automatically garbage-collected.
- **Invariant:** Every (eligible) node always has a copy of the Pod.

---

## 2. Use Cases 🎯

| Use Case | Example | Why DaemonSet |
|---|---|---|
| Monitoring agent | Prometheus node-exporter, Datadog agent | Per-node metrics collection |
| Log collector | Fluentd, Filebeat, Fluent Bit | Per-node log shipping |
| kube-proxy | Runs on every worker node | Required on all nodes; deployable as a DaemonSet |
| CNI / networking agent | Calico, Weave Net, Cilium | Agent needed on each node |

> No manual add/remove of agents when the cluster scales. The DaemonSet controller handles it.

---

## 3. Definition File 🏗️

Structure is nearly identical to a ReplicaSet: `apiVersion`, `kind`, `metadata`, `spec`.

- `apiVersion`: `apps/v1`
- `kind`: `DaemonSet` (instead of `ReplicaSet`)
- `spec.selector` + `spec.template` (nested Pod spec)
- ⚠️ **`selector.matchLabels` MUST match `template.metadata.labels`**, otherwise the API server rejects the object.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: monitoring-daemon
spec:
  selector:
    matchLabels:
      app: monitoring-agent
  template:
    metadata:
      labels:
        app: monitoring-agent
    spec:
      containers:
        - name: monitoring-agent
          image: monitoring-agent
```

```bash
# Create
kubectl create -f daemon-set-definition.yaml

# List
kubectl get daemonsets

# Detailed view
kubectl describe daemonset monitoring-daemon
```

## 5. Internal Mechanics: How Scheduling Works ⚙️

**Problem:** How do you place one Pod on each node?

| Era | Mechanism |
|---|---|
| **Before v1.12** | Set `spec.nodeName` on each Pod → **bypasses kube-scheduler**, binds directly to the node |
| **v1.12 onwards** | DaemonSet uses the **default scheduler + NodeAffinity** rules to place Pods on target nodes |

- Modern approach: the DaemonSet controller injects a `nodeAffinity` term (matching the node name) into each Pod, so the **default scheduler** binds it.
- Benefit: Pods go through the normal scheduling path (respects taints/tolerations, priorities, etc.), unlike the direct `nodeName` bypass.

---

## 🚀 Summary Cheat Sheet

- **Core guarantee:** 1 Pod per node, auto-managed as nodes join or leave.
- **Typical workloads:** monitoring agents, log collectors, kube-proxy, CNI agents.
- **YAML delta from ReplicaSet:** `kind: DaemonSet`, no `replicas` field.
- **Gotcha:** `selector.matchLabels` must equal `template.metadata.labels`.
- **Scheduling:** `nodeName` (≤ v1.11) → default scheduler + NodeAffinity (≥ v1.12).
- **Commands:** `kubectl create -f`, `kubectl get daemonsets`, `kubectl describe daemonset <name>`.
