# 🧭 Multiple Schedulers: Custom Scheduling Logic

## 1. Why Multiple Schedulers? 📝

- **Default scheduler:** Distributes pods across nodes using filtering/scoring, honouring taints & tolerations, node affinity, resource requests, etc.
- **Gap:** Some apps need **custom placement logic / additional checks** that the default algorithm can't express.
- **Solution:** Kubernetes is extensible. Write your own scheduler, package it, and run it as:
  - the **default** scheduler, or
  - an **additional** scheduler alongside the default.
- **Result:** Most workloads use the default scheduler; specific workloads opt in to a custom one.
- **Hard requirement:** Every scheduler must have a **unique name**.

---

## 2. Scheduler Naming & Config File 🏷️

- Default scheduler name: **`default-scheduler`** (applied automatically if no name is configured).
- Name is set in a **KubeSchedulerConfiguration** file.

```yaml
# my-scheduler-config.yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: my-custom-scheduler
```

- Each additional scheduler → **its own config file with its own `schedulerName`**.

---

## 3. Deployment Methods 🏗️

### Method 1: Standalone Binary / Service (simplest, rarely used today)

- Use the same `kube-scheduler` binary (or your own custom-built one) and point it at the custom config.

```bash
kube-scheduler --config=/etc/kubernetes/my-scheduler-config.yaml
```

- Additional options normally required: `--kubeconfig` for authentication to kube-apiserver.
- ⚠️ **Not how it's done ~99% of the time**: under **kubeadm**, control plane components run as **pods/deployments** in the cluster.

### Method 2: As a Pod

- Pod definition runs the scheduler container with:
  - `--kubeconfig=<scheduler.conf>`: auth to the API server
  - `--config=<custom scheduler config>`: picks up `schedulerName`
- **`leaderElect` option** (in scheduler config):
  - Needed when **multiple copies** of the *same* scheduler run on different master nodes (HA).
  - Only **one is active** at a time; leader election picks who leads.
  - Pass an additional **lock object name** (`resourceName`) to **differentiate the custom scheduler's election from the default scheduler's**.

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: my-custom-scheduler
leaderElection:
  leaderElect: true
  resourceNamespace: kube-system
  resourceName: lock-object-my-scheduler
```

### Method 3: As a Deployment (per Kubernetes docs: *Configure Multiple Schedulers*)

- Same as the pod approach but wrapped in a `Deployment`.
- Image: custom `kube-scheduler` image; command points to the config file.
- **Prerequisites:** ServiceAccount + ClusterRole/ClusterRoleBinding (auth).
- **Config injection:**
  - Option A: local file → **volume mount**
  - Option B (used in the docs): **ConfigMap** holding the `KubeSchedulerConfiguration` → mounted as a **volume** at the path passed to `--config`
- With `replicas: 1`, `leaderElect` can be `false`.

---

## 4. Verifying the Scheduler is Running ✅

```bash
kubectl get pods -n kube-system
```

- Pod deployment → pod named after your manifest.
- Deployment → slightly different naming (suffix hashes).
- ⚠️ Check the **correct namespace**.

---

## 5. Using the Custom Scheduler in a Pod 🎯

Add **`spec.schedulerName`** to the Pod (or the pod template of a Deployment).

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  schedulerName: my-custom-scheduler
  containers:
    - name: nginx
      image: nginx
```

```bash
kubectl create -f pod-definition.yaml
```

| Pod state | Meaning |
|---|---|
| `Running` | Custom scheduler picked it up and bound it |
| `Pending` | Scheduler **misconfigured / not running / name mismatch** |

---

## 6. Troubleshooting & Verification 🔍

**Which scheduler scheduled the pod?** Check events; the `Scheduled` event's **source** is the scheduler name.

```bash
kubectl get events -o wide
```

- Look for the `Scheduled` event → source = `my-custom-scheduler`, message = "Successfully assigned ...".

**Pod stuck in Pending:**

```bash
kubectl describe pod nginx
```

**Scheduler logs:**

```bash
kubectl logs my-custom-scheduler -n kube-system
```

---

## 🚀 Summary Cheat Sheet

- **Multiple schedulers can coexist**; each needs a **unique `schedulerName`**.
- **Default name:** `default-scheduler`.
- **Config:** `KubeSchedulerConfiguration` → `profiles[].schedulerName`.
- **Deploy as:** service (legacy), **Pod**, or **Deployment** (kubeadm-era norm). Needs `--kubeconfig` + `--config`.
- **HA:** `leaderElect: true` + a distinct **lock object name** to avoid clashing with the default scheduler's election.
- **Deployment prereqs:** ServiceAccount, ClusterRole/ClusterRoleBinding, ConfigMap + volume mount for config.
- **Consume:** `spec.schedulerName: <name>` on the pod.
- **Debug:** `Pending` → `kubectl describe pod`; `kubectl get events -o wide`; `kubectl logs <scheduler> -n kube-system`.
