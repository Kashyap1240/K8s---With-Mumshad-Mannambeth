# 🧩 Scheduler Profiles: Plugins & Extension Points

## 1. Scheduling Pipeline Recap 🔄

Worked example: a pod requesting **10 CPU**, with 4 candidate nodes.

| Phase | What happens | Example |
|---|---|---|
| **1. Scheduling Queue** | Pods wait; **sorted by priority** (`PriorityClass`) | High-priority pod (value 1,000,000) moves to the head |
| **2. Filter** | Nodes that **cannot** run the pod are removed | Nodes with < 10 CPU free are dropped |
| **3. Score** | Remaining nodes scored (weighted) | Node leaving 6 CPU free outscores one leaving 2 |
| **4. Bind** | Pod **bound** to the highest-scoring node | Node with the highest score wins |

> Priority is set via a `PriorityClass` (`name`, `value`) referenced from the pod.

---

## 2. Default Plugins per Phase 🔌

All phase logic is implemented by **plugins**.

| Phase | Plugin | Function |
|---|---|---|
| Queue | `PrioritySort` | Orders pods by `PriorityClass` value |
| Filter | `NodeResourcesFit` | Drops nodes lacking required resources |
| Filter | `NodeName` | If `spec.nodeName` set, drops non-matching nodes |
| Filter | `NodeUnschedulable` | Drops nodes with `unschedulable: true` (cordoned) |
| Score | `NodeResourcesFit` | Scores by resources left after allocation |
| Score | `ImageLocality` | Higher score for nodes already holding the container image |
| Bind | `DefaultBinder` | Performs the actual binding |

- A **single plugin can span multiple phases** (e.g. `NodeResourcesFit` → filter + score).
- ⚠️ **Score-phase plugins don't reject nodes.** `ImageLocality` only *prefers* nodes with the image; if none have it, the pod is still placed on a node without it.

---

## 3. Extension Points 🪝

Each phase exposes **extension points** where plugins attach. You can plug in **custom code at any point**.

```
Scheduling Queue → queueSort
Filter stage     → preFilter → filter → postFilter
Score stage      → preScore  → score  → reserve
Binding stage    → permit → preBind → bind → postBind
```

| Extension point | Position |
|---|---|
| `queueSort` | Ordering in the scheduling queue |
| `preFilter` | Before filter |
| `filter` | Eliminate infeasible nodes |
| `postFilter` | After filter (e.g. preemption when no node fits) |
| `preScore` | Before score |
| `score` | Rank feasible nodes |
| `reserve` | After score |
| `permit` | Before bind |
| `preBind` | Before bind |
| `bind` | Bind pod to node |
| `postBind` | After bind |

- Some default plugins span multiple extension points; others sit at only one.

---

## 4. Problem with Multiple Scheduler Binaries ⚠️

Running `default-scheduler`, `my-scheduler`, `my-scheduler-2` as **separate binaries** (each with own config):

- **Operational overhead:** multiple processes to maintain.
- **Race conditions:** independent schedulers may place workloads on the **same node simultaneously**, with no shared view of the decision.

---

## 5. Solution: Multiple Profiles in a Single Scheduler 🏗️

- **Introduced in Kubernetes v1.18.**
- One `kube-scheduler` binary hosts **multiple profiles**; each profile has its own `schedulerName` and acts as a **separate logical scheduler**.
- Eliminates cross-process races and the extra binaries.

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: my-scheduler-1
  - schedulerName: my-scheduler-2
  - schedulerName: my-scheduler-3
```

- Without further config, every profile behaves like the **default scheduler**.

---

## 6. Customizing Plugins per Profile ⚙️

Under each profile, use **`plugins.<extensionPoint>.enabled / disabled`** (by name or `"*"` pattern).

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: my-scheduler-1

  - schedulerName: my-scheduler-2
    plugins:
      filter:
        disabled:
          - name: TaintToleration
      score:
        disabled:
          - name: TaintToleration
        enabled:
          - name: MyCustomPlugin

  - schedulerName: my-scheduler-3
    plugins:
      preScore:
        disabled:
          - name: "*"
      score:
        disabled:
          - name: "*"
```

| Profile | Behaviour |
|---|---|
| `my-scheduler-1` | Default behaviour |
| `my-scheduler-2` | `TaintToleration` disabled; custom plugin enabled |
| `my-scheduler-3` | **All** `preScore` + `score` plugins disabled |

- `MyCustomPlugin` is a placeholder for a plugin you've compiled into your scheduler build.
- Pods target a profile via `spec.schedulerName: <profile name>`.

## 🚀 Summary Cheat Sheet

- **Pipeline:** Scheduling Queue (sort) → Filter → Score → Bind.
- **Default plugins:** `PrioritySort`, `NodeResourcesFit`, `NodeName`, `NodeUnschedulable`, `ImageLocality`, `DefaultBinder`.
- **Filter = hard rejection. Score = soft preference only.**
- **Extension points:** `queueSort`, `preFilter`, `filter`, `postFilter`, `preScore`, `score`, `reserve`, `permit`, `preBind`, `bind`, `postBind`.
- **Multiple binaries** → maintenance burden + scheduling race conditions.
- **Profiles (v1.18+)** → many logical schedulers in **one binary**, each with a unique `schedulerName`.
- **Customize** via `plugins.<extensionPoint>.enabled/disabled` per profile; `"*"` disables all at that point.
