# ReplicaSets & Replication Controllers

## 1. Why Do We Need Replication? 🧬
Controllers are the "brain" behind Kubernetes — processes that continuously monitor objects and respond as needed. The **Replication Controller** is one such controller.

* **High Availability**: If you have a single pod running your app and it crashes, users lose access. Running **multiple instances** of the pod ensures that if one fails, others are still serving traffic.
* **Works even for 1 pod**: Even if you want just a single pod, a replication controller helps by automatically spinning up a new pod if the existing one fails.
* **Load Balancing & Scaling**: Beyond fault tolerance, replication also lets you spread load across multiple pods — and across multiple nodes — as demand increases.

## 2. Replication Controller vs ReplicaSet ⚖️

| | Replication Controller | ReplicaSet |
|---|---|---|
| Status | Older technology | Newer, **recommended** technology |
| Purpose | Same — ensure desired number of pods are running | Same — ensure desired number of pods are running |
| `apiVersion` | `v1` | `apps/v1` |
| `selector` field | Optional (defaults to pod labels if skipped) | **Required** — must use `matchLabels` |

📌 Going forward, **ReplicaSet** is the preferred choice for all demos/implementations.

## 3. Creating a Replication Controller 📝

A definition file has the same 4 root sections as a Pod: `apiVersion`, `kind`, `metadata`, `spec`.

```yaml
apiVersion: v1
kind: ReplicationController
metadata:
  name: myapp-rc
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
  replicas: 3
```

**Key points:**
- The **`template`** section holds the entire Pod definition (reuse your existing pod YAML, minus its own `apiVersion`/`kind` lines) — it becomes a **child** of `spec`.
- **`replicas`** and **`template`** are **siblings** under `spec` — they must be aligned at the same indentation level.
- This nests two definition files together: the Replication Controller (parent) and the Pod (child) — resulting in **two `metadata`** sections and **two `spec`** sections in one file.

**Commands:**
```bash
kubectl create -f rc-definition.yaml     # Create the RC
kubectl get replicationcontroller        # View RC (shows Desired, Current, Ready counts)
kubectl get pods                         # View the pods it created (named myapp-rc-xxxxx)
```

## 4. Creating a ReplicaSet 📝

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-replicaset
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
  replicas: 3
  selector:
    matchLabels:
      type: front-end
```

⚠️ **Common Error**: Using `apiVersion: v1` for a ReplicaSet will throw:
Make sure to use `apps/v1`.

**Commands:**
```bash
kubectl create -f replicaset-definition.yaml
kubectl get replicaset       # or: kubectl get rs
kubectl get pods
```

## 5. Labels & Selectors — Why They Matter 🏷️

* The **`selector`** tells the ReplicaSet **which pods to monitor**.
* **Required** for ReplicaSet (must be written as `matchLabels`), but **optional** for Replication Controller (defaults to the pod template's labels if omitted).
* **Why it matters**: A ReplicaSet can monitor pods that **already existed before** the ReplicaSet was created — as long as their labels match the `selector`. It doesn't only manage pods it created itself.

**Example scenario:**
- You already have 3 running front-end pods (created manually, not via ReplicaSet).
- You create a ReplicaSet with `replicas: 3` and a `selector` matching those pods' labels.
- The ReplicaSet sees 3 pods already match → **does nothing** initially (no new pods created).
- ✅ But the `template` section is still **required** — if one of those existing pods fails later, the ReplicaSet needs the template to create a replacement.

## 6. Scaling a ReplicaSet 📈

There are **two ways** to scale (e.g., from 3 → 6 replicas):

**Option A: Edit the file, then replace**
```bash
# Update `replicas: 6` in the YAML file first
kubectl replace -f replicaset-definition.yaml
```

**Option B: Use the `scale` command directly**
```bash
kubectl scale --replicas=6 -f replicaset-definition.yaml
# OR
kubectl scale --replicas=6 replicaset myapp-replicaset
```

⚠️ **Important**: If you scale using the `scale` command with the **file** as input, the `replicas` value **inside the file itself is NOT updated** — it'll still say `3` even though the cluster now runs 6. Keep this in mind to avoid confusion later.

> 📌 Auto-scaling based on load is possible too, but that's a more advanced topic covered later.

## 🚀 Summary Cheat Sheet
| Command | Purpose |
|---|---|
| `kubectl create -f <file>.yaml` | Create a ReplicaSet/Replication Controller |
| `kubectl get replicaset` / `kubectl get rs` | List ReplicaSets |
| `kubectl get replicationcontroller` | List Replication Controllers |
| `kubectl get pods` | List pods created |
| `kubectl delete replicaset <name>` | Delete a ReplicaSet |
| `kubectl replace -f <file>.yaml` | Update RS after editing the file |
| `kubectl scale --replicas=<n> -f <file>.yaml` | Scale RS without editing the file |

* **Role**: Ensures the desired number of pod replicas are always running (self-healing + scaling).
* **Structure**: `template` (pod spec) + `replicas` (count) + `selector` (which pods to manage) — all siblings under `spec`.
* **Prefer ReplicaSet over Replication Controller** going forward — same concept, newer API (`apps/v1`), and requires an explicit `selector`.
