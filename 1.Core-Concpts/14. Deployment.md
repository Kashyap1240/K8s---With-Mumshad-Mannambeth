# Kubernetes Deployments

## 1. Why Do We Need Deployments? 🚀

Before diving into the object itself, think about how you'd actually run an application in production:

- You need multiple instances of your app running (not just one) for reliability.
- When a new version of your app becomes available, you want to upgrade seamlessly — without downtime.
- Upgrades shouldn't happen to all instances at once — that could disrupt users. Instead, you want to upgrade them one at a time → this is called a Rolling Update.
- If an upgrade breaks something, you want the ability to roll back to the previous working version.
- Sometimes you want to make multiple changes at once (upgrade version + scale + change resources), pause all of them, and then apply everything together — rather than triggering an action per command.

📌 All of these capabilities are exactly what Kubernetes Deployments provide.

## 2. Where Deployment Fits in the Hierarchy 🏗️

| Object | Role |
|---|---|
| Pod | Deploys a single instance of the application (one or more containers). |
| ReplicaSet / Replication Controller | Deploys multiple instances (pods) of the application. |
| Deployment | Sits above ReplicaSet — manages ReplicaSets, and adds rolling updates, rollbacks, pause/resume. |

A Deployment is a Kubernetes object that sits higher in the hierarchy than ReplicaSets, giving you seamless upgrades, rollback, and pause/resume capabilities.

## 3. Creating a Deployment 📝

A Deployment definition file looks almost identical to a ReplicaSet definition file — the only difference is the kind.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
  replicas: 3
  selector:
    matchLabels:
      type: front-end

Structure recap:
- apiVersion: apps/v1
- metadata: name, labels
- spec: contains template (pod definition), replicas, and selector — same as ReplicaSet.

## 4. What Happens Behind the Scenes ⚙️

When you create a Deployment, it doesn't create pods directly — it creates a chain:

Deployment → creates → ReplicaSet → creates → Pods

Commands:

kubectl create -f deployment-definition.yaml   # Create the deployment
kubectl get deployments                        # View the deployment
kubectl get replicaset                         # View the auto-created ReplicaSet (named after the deployment)
kubectl get pods                               # View the pods (named after deployment + replicaset)

📌 At this stage, functionally there isn't much difference from a plain ReplicaSet — except that a new object type (Deployment) now exists on top, which will unlock rolling updates, rollbacks, and pause/resume in upcoming lectures.

## 5. Viewing Everything at Once 👀

kubectl get all

This shows all created objects together — in this case: the Deployment, its ReplicaSet, and the resulting Pods (e.g. 3 pods, matching the replicas: 3 count).

## 🚀 Summary Cheat Sheet

| Command | Purpose |
|---|---|
| kubectl create -f <file>.yaml | Create a Deployment |
| kubectl get deployments | List Deployments |
| kubectl get replicaset | List ReplicaSets (auto-created by Deployment) |
| kubectl get pods | List Pods (auto-created by ReplicaSet) |
| kubectl get all | View all objects (Deployment + ReplicaSet + Pods) together |

- Hierarchy: Pod → ReplicaSet → Deployment.
- Deployment definition = same as ReplicaSet definition, just kind: Deployment.
- Key capabilities unlocked by Deployment: Rolling updates, Rollbacks, Pause & Resume changes.
- Auto-creation chain: Creating a Deployment automatically creates a ReplicaSet, which automatically creates Pods.
