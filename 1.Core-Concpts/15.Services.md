## 1. Why Do We Need Services? 🚀

Think about how an application actually runs in a cluster:

- Your app is split into **groups of pods**: a front-end group serving users, a back-end group running processes, and another group connecting to an external data source.
- These groups need to **talk to each other** and to **users outside the cluster**.
- Pod IPs live on an **internal pod network**, so they can't be reached directly from outside.
- Pods come and go, so you need something stable in front of them.

📌 A **Service** is the object that solves all of this. It enables connectivity between groups of pods, exposes the front end to end users, connects to external data sources, and gives **loose coupling between microservices**.

## 2. The Problem: Reaching a Pod from Outside 🌐

| Component         | IP / Network  |
|-------------------|---------------|
| Laptop            | `192.168.1.1` |
| Kubernetes node   | `192.168.1.2` |
| Pod network range | `10.244.0.0`  |
| Pod               | `10.244.0.2`  |

- The laptop **cannot** ping or reach `10.244.0.2`, because it is on a separate network.
- SSH into the node and `curl http://10.244.0.2` works, but only from inside the node.
- What we want: open `http://<node-ip>:<port>` from the laptop.
- So we need something in the middle that maps **laptop → node → pod**. That is a Service.

## 3. Types of Services 🧩

| Type             | What it does                                                                 | Example use case                      |
|------------------|------------------------------------------------------------------------------|---------------------------------------|
| **NodePort**     | Makes a pod accessible on a port on the node                                 | External access to a web app          |
| **ClusterIP**    | Creates a virtual IP inside the cluster                                      | Front-end pods ↔ back-end pods        |
| **LoadBalancer** | Provisions a load balancer in supported cloud providers                      | Distribute load across web servers    |

A Service is a Kubernetes object, just like Pods, ReplicaSets and Deployments.

## 4. NodePort Service in Detail 🔌

### The three ports (from the viewpoint of the Service)

```
User ──► NodePort (on node) ──► Port (on Service) ──► TargetPort (on Pod)
         30008                   80                    80
```

| Port         | Lives on     | Notes                                                                               |
|--------------|--------------|-------------------------------------------------------------------------------------|
| `targetPort` | The **pod**  | Where the web server runs; the Service forwards requests here                       |
| `port`       | The **Service** | The Service is like a virtual server in the cluster with its own IP, the **ClusterIP** |
| `nodePort`   | The **node** | Used for external access. Valid range: **30000–32767**                              |

## 5. Creating a Service 📝

The file has the usual four sections: `apiVersion`, `kind`, `metadata`, `spec`.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  ports:
    - targetPort: 80
      port: 80
      nodePort: 30008
  selector:
    app: myapp
    type: front-end
```

Field rules:

- `apiVersion` is `v1` and `kind` is `Service`.
- `spec.type` can be `ClusterIP`, `NodePort` or `LoadBalancer`.
- **Only `port` is mandatory.**
  - No `targetPort` → assumed to be the same as `port`.
  - No `nodePort` → a free port in 30000–32767 is allocated automatically.
- `ports` is an **array** (note the `-`), so one Service can have multiple port mappings.

## 6. Linking the Service to Pods: Labels & Selectors 🔗

Nothing in the ports section says *which* pod to send traffic to. There could be hundreds of pods serving on port 80.

- Use **labels and selectors**, the same technique used by ReplicaSets.
- Copy the labels from the pod definition into `spec.selector` of the Service.

Pod definition with the matching labels:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
    type: front-end
spec:
  containers:
    - name: nginx-container
      image: nginx
```

## 7. Commands ⚙️

```bash
kubectl create -f service-definition.yaml   # Create the Service
kubectl get services                        # List Services (type, cluster IP, port mappings)
curl http://192.168.1.2:30008               # Access the app from outside the cluster
```

## 8. Behaviour in Different Scenarios 👀

| Scenario                          | What happens                                                                                                 |
|-----------------------------------|--------------------------------------------------------------------------------------------------------------|
| **Single pod, single node**       | Service maps node port → pod target port                                                                     |
| **Multiple pods, single node**    | All pods matching the selector become **endpoints**. Traffic is balanced using a **random algorithm**        |
| **Multiple pods, multiple nodes** | Service **spans all nodes** and exposes the same `nodePort` on each. Use **any node's IP** + the same port   |

📌 In every case the Service is created exactly the same way. When pods are added or removed, the Service updates automatically, and you rarely need to change it afterwards.

## 🚀 Summary Cheat Sheet

| Command / Concept                      | Purpose                                      |
|----------------------------------------|----------------------------------------------|
| `kubectl create -f <file>.yaml`        | Create a Service                             |
| `kubectl get services`                 | List Services                                |
| `curl http://<node-ip>:<nodePort>`     | Access the app externally                    |

- Service types: **NodePort** (external), **ClusterIP** (internal), **LoadBalancer** (cloud).
- Three ports: `targetPort` (pod), `port` (service), `nodePort` (node).
- NodePort range: **30000–32767**.
- Only `port` is mandatory; the other two have defaults.
- Services find pods using **selector ↔ pod labels**.
- Built-in load balancing across matching pods is **random**.
- The same NodePort is opened on **all nodes** in the cluster.
