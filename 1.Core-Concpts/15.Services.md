## 1. Why Do We Need Services? 🚀

An application is usually split into **groups of pods**:

- A front-end group serving users
- A back-end group running processes
- A group connecting to an external data source (or running Redis / MySQL)

These groups need to talk to each other and to the outside world, but:

- Pod IPs are **not static**. Pods die and new ones are created all the time.
- Pods live on an **internal pod network** that outsiders can't reach.
- With many identical pods, someone has to decide **which pod** gets a request.

📌 A **Service** is a Kubernetes object (like Pods, ReplicaSets, Deployments) that groups pods behind a **single stable interface**. It enables connectivity between pod groups, exposes the front end to users, and connects to external data sources. This gives **loose coupling between microservices**.

---

## 2. Types of Services 🧩

| Type             | What it does                                                     | Typical use                              |
|------------------|------------------------------------------------------------------|------------------------------------------|
| **NodePort**     | Exposes a pod on a port on every node                            | External access to an app                |
| **ClusterIP**    | Creates a virtual IP inside the cluster                          | Communication between tiers (front ↔ back) |
| **LoadBalancer** | Provisions a cloud provider's load balancer                      | Single public URL for the front end      |

## 3. NodePort 🔌

### The problem: reaching a pod from outside 🌐

| Component         | IP / Network  |
|-------------------|---------------|
| Laptop            | `192.168.1.1` |
| Kubernetes node   | `192.168.1.2` |
| Pod network range | `10.244.0.0`  |
| Pod               | `10.244.0.2`  |

- The laptop **cannot** reach `10.244.0.2` because it is on a separate network.
- SSH into the node and `curl http://10.244.0.2` works, but only from inside the node.
- We want to open `http://<node-ip>:<port>` from the laptop, so a Service must map **laptop → node → pod**.

### The three ports (from the viewpoint of the Service)

```
User ──► NodePort (on node) ──► Port (on Service) ──► TargetPort (on Pod)
         30008                   80                    80
```

| Port         | Lives on        | Notes                                                                                  |
|--------------|-----------------|----------------------------------------------------------------------------------------|
| `targetPort` | The **pod**     | Where the web server runs; the Service forwards requests here                          |
| `port`       | The **Service** | The Service acts like a virtual server in the cluster with its own IP, the **ClusterIP** |
| `nodePort`   | The **node**    | Used for external access. Valid range: **30000–32767**                                 |

### Service definition file 📝

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  ports:
    - targetPort: 80
      port: 80
      nodePort: 30008
  selector:
    app: myapp
    type: front-end
```

Field rules:

- `apiVersion` is `v1` and `kind` is `Service`.
- `spec.type` can be `ClusterIP`, `NodePort` or `LoadBalancer`.
- **Only `port` is mandatory.**
  - No `targetPort` → assumed to be the same as `port`.
  - No `nodePort` → a free port in 30000–32767 is allocated automatically.
- `ports` is an **array** (note the `-`), so one Service can have multiple port mappings.

### Linking the Service to pods: labels & selectors 🔗

Nothing in `ports` says *which* pod to target, and hundreds of pods could be serving on port 80. So we use **labels and selectors** (same technique as ReplicaSets): copy the labels from the pod definition into `spec.selector`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: myapp
    type: front-end
spec:
  containers:
    - name: nginx-container
      image: nginx
```

### Commands ⚙️

```bash
kubectl create -f service-definition.yaml   # Create the Service
kubectl get services                        # List Services (type, cluster IP, port mappings)
curl http://192.168.1.2:30008               # Access the app from outside the cluster
```

### Behaviour in different scenarios 👀

| Scenario                          | What happens                                                                                                |
|-----------------------------------|-------------------------------------------------------------------------------------------------------------|
| **Single pod, single node**       | Service maps node port → pod target port                                                                    |
| **Multiple pods, single node**    | All pods matching the selector become **endpoints**. Traffic is balanced using a **random algorithm**       |
| **Multiple pods, multiple nodes** | Service **spans all nodes** and exposes the same `nodePort` on each. Use **any node's IP** + the same port  |

📌 The Service is created the same way in every case. When pods are added or removed, it updates automatically.

## 4. ClusterIP 🕸️

### Why we need it

A full-stack app has multiple tiers of pods:

```
Front end ──► Back end ──► Redis
                      └──► MySQL
```

- Pod IPs are **not static**, so they can't be relied on for internal communication.
- If a front-end pod (e.g. `10.244.0.3`) needs the back end, **which of the back-end pods** does it pick, and **who decides**?

### How it works

- A Service groups all back-end pods and exposes **one single interface**.
- Requests are forwarded to one of the pods **randomly**.
- Create similar Services for Redis, MySQL, etc.
- Each Service gets an **IP and a name inside the cluster**. Other pods should use this **name** to reach it.
- This type is called **ClusterIP**.

✅ Each layer can **scale or move** without affecting communication between the others, which makes microservices easy to deploy.

### Service definition file 📝

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  type: ClusterIP
  ports:
    - targetPort: 80
      port: 80
  selector:
    app: myapp
    type: back-end
```

| Field        | Meaning                                                                    |
|--------------|----------------------------------------------------------------------------|
| `name`       | `backend`, the name other pods use to reach the Service                    |
| `type`       | `ClusterIP`. This is the **default**, so it can be omitted                 |
| `targetPort` | Port on the **pod** where the back end is exposed                          |
| `port`       | Port on the **Service** where it is exposed                                |
| `selector`   | Labels copied from the pod definition; links Service → pods                |

### Commands

```bash
kubectl create -f service-definition.yaml
kubectl get services
```

Other pods access the Service using its **ClusterIP** or its **name** (`backend`).

## 5. LoadBalancer ☁️

### The problem with NodePort alone

Example: a 4-node cluster running the **voting app** and **result app** (front ends), each exposed through a NodePort Service.

- Users can reach each app via **any node's IP + the Service's port**, which gives a separate IP:port URL per node for each app.
- This works **even if the pods run on only two of the nodes**. The port is opened on all nodes.
- But end users don't want that. They want **one URL**, like `example-voting-app.com`.

### Options to get a single URL

| Option                                              | Notes                                                                 |
|-----------------------------------------------------|-----------------------------------------------------------------------|
| Create a separate VM with **HAProxy / nginx** and route traffic to the nodes | Tedious to set up, maintain and manage            |
| Use the **cloud provider's native load balancer** via Kubernetes | Kubernetes integrates and configures it for you ✅   |

### How to use it

Just change the Service type from `NodePort` to `LoadBalancer`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: voting-app-service
spec:
  type: LoadBalancer
  ports:
    - targetPort: 80
      port: 80
  selector:
    app: voting-app
```

### ⚠️ Supported platforms only

- Works on supported cloud platforms: **GCP, AWS, Azure**.
- On unsupported environments (e.g. **VirtualBox**, local setups), `type: LoadBalancer` has the **same effect as NodePort**. The Service is exposed on a high port on the nodes, and **no external load balancer is configured**.

## 6. Comparison of All Three 📊

| Feature              | ClusterIP                | NodePort                         | LoadBalancer                          |
|----------------------|--------------------------|----------------------------------|---------------------------------------|
| Accessible from      | Inside the cluster only  | Outside, via `<NodeIP>:<NodePort>` | Outside, via one external IP / URL  |
| Typical use          | Tier-to-tier traffic     | Simple external access / testing | Production front ends on the cloud    |
| Port on node         | No                       | Yes (30000–32767)                | Yes (also created)                    |
| Extra infrastructure | None                     | None                             | Cloud provider's load balancer        |
| Works everywhere     | ✅                       | ✅                               | ❌ Only on supported cloud platforms  |

## 🚀 Summary Cheat Sheet

| Command / Concept                  | Purpose                                         |
|------------------------------------|-------------------------------------------------|
| `kubectl create -f <file>.yaml`    | Create a Service                                |
| `kubectl get services`             | List Services (type, cluster IP, ports)         |
| `curl http://<node-ip>:<nodePort>` | Access a NodePort Service externally            |

- Pod IPs are **not stable**, so Services give pods a stable access point.
- **ClusterIP** (default): internal communication between tiers.
- **NodePort**: external access on a node port. Range is **30000–32767**.
- **LoadBalancer**: a single external URL using the cloud's native load balancer (**GCP / AWS / Azure** only).
- On unsupported platforms, LoadBalancer behaves like NodePort.
- Ports: `targetPort` (pod), `port` (service), `nodePort` (node). Only `port` is mandatory.
- Services find pods using **selector ↔ pod labels**.
- Load balancing across matching pods is **random**.
- NodePort opens the **same port on all nodes**, even those without the pods.
- When pods are added or removed, the Service updates automatically.
