## 1. What is a Namespace? 🏠

Analogy: two boys are both named Mark, one from the **Smith** house and one from the **Williams** house.

- Inside their own house, people simply say **"Mark"**.
- To refer to the Mark in the *other* house, or when speaking from outside, you use the **full name** (Mark Smith / Mark Williams).
- Each house has its **own rules** (who does what) and its **own resources** it can consume.

📌 In Kubernetes, **houses = namespaces**. A namespace is a way to **isolate resources** inside one cluster.

## 2. Default Namespaces 📦

Everything so far (pods, deployments, services) was created in the **default** namespace. Kubernetes creates three namespaces automatically:

| Namespace     | Purpose                                                                                                   |
|---------------|-----------------------------------------------------------------------------------------------------------|
| `default`     | Where your resources go unless you specify otherwise                                                      |
| `kube-system` | Kubernetes' own internal pods and services (networking solution, DNS service, etc.). Kept separate so you don't accidentally modify or delete them |
| `kube-public` | Resources that should be **available to all users**                                                       |

## 3. When Should You Use Your Own Namespaces? 🤔

- **Small cluster / learning:** just stay in `default`.
- **Enterprise / production:** use namespaces to separate things.

Example: one cluster for both **dev** and **prod**, with a namespace for each.

✅ Benefits:

- **Isolation:** working in dev, you can't accidentally modify prod resources.
- **Policies:** each namespace can have its own policies defining who can do what.
- **Resource quotas:** each namespace is guaranteed a certain amount of resources and can't exceed its limit.

## 4. DNS: How Resources Reach Each Other 🌐

**Within the same namespace:** use just the name (like a family using first names).

```
mysql.connect("db-service")
```

**Across namespaces:** append the namespace (like using the full name).

```
mysql.connect("db-service.dev.svc.cluster.local")
```

A DNS entry in this format is added **automatically** when a Service is created:

```
db-service . dev . svc . cluster.local
    │         │     │        │
    │         │     │        └── default domain of the cluster
    │         │     └─────────── subdomain for services
    │         └───────────────── namespace
    └─────────────────────────── service name
```

## 5. Working with Namespaces: Commands ⚙️

```bash
# List pods in the default namespace
kubectl get po

# List pods in another namespace (-n = --namespace)
kubectl get po -n kube-system

# Create a resource in a specific namespace
kubectl create -f pod-definition.yaml -n dev

# List pods across ALL namespaces (-A = --all-namespaces)
kubectl get po -A
```

💡 **Shortcuts:** `po` = pods, `svc` = services, `deploy` = deployments, `ns` = namespaces, `-n` = namespace, `-A` = all namespaces.

⚠️ `-n` only matters for **namespaced** resources (pods, services, deployments...). **Nodes are cluster-wide**, so `kubectl get no -n dev` just ignores `-n`.

### Always create in a namespace (via the YAML)

Put the namespace under `metadata`, so the resource goes there even if you don't pass `--namespace`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  namespace: dev
  labels:
    app: myapp
spec:
  containers:
    - name: nginx-container
      image: nginx
```

## 6. Creating a Namespace 📝

**Option 1: definition file**

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dev
```

```bash
kubectl create -f namespace-dev.yaml
```

**Option 2: one-liner**

```bash
kubectl create ns dev
```

## 7. Switching Namespace Permanently 🔀

By default you're in `default`, so you need `--namespace` for anything else. To switch your **current context** to `dev`:

```bash
kubectl config set-context --current --namespace=dev
```

After that, `kubectl get po` lists pods in **dev**, and you'd need `-n` for `default` or `prod`.

💡 There is no `kubectl set ns` command. The command above is the built-in way. The optional **`kubens`** tool (part of `kubectx`) gives a shorter version: `kubens dev`.

📌 This command finds the **current context** and sets the namespace for it. A **context** is used to manage multiple clusters and environments from the same system (covered in a separate lecture).

## 8. Resource Quota 📏

To limit the resources a namespace can use, create a **ResourceQuota** and specify the namespace it applies to:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: dev
spec:
  hard:
    pods: "10"
    requests.cpu: "10"
    requests.memory: 10Gi
    limits.cpu: "10"
    limits.memory: 10Gi
```

```bash
kubectl create -f compute-quota.yaml -n dev
```

## 🚀 Summary Cheat Sheet

| Command / Concept                                                  | Purpose                                       |
|--------------------------------------------------------------------|-----------------------------------------------|
| `kubectl get po -n <ns>`                                           | List pods in a namespace                      |
| `kubectl get po -A`                                                | List pods in every namespace                  |
| `kubectl create -f <file>.yaml -n <ns>`                            | Create a resource in a namespace              |
| `kubectl create ns <ns>`                                           | Create a namespace                            |
| `kubectl config set-context --current --namespace=<ns>`            | Switch the current namespace                  |

- Namespaces = **isolation** inside one cluster (the "houses").
- Built-in: `default`, `kube-system`, `kube-public`.
- Same namespace → use the **service name**. Different namespace → `<service>.<namespace>.svc.cluster.local`.
- Set `namespace:` under `metadata` in YAML to always deploy to the same namespace.
- Each namespace can have its own **policies** and **resource quotas**.
- Switching namespaces permanently is done through the **context**.
