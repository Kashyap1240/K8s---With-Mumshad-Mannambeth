# Imperative vs Declarative in Kubernetes (and how `kubectl apply` works)

## 1. Two Approaches to Managing Infrastructure 🚕

Analogy: visiting a friend's house.

| Approach        | Analogy                                                                 | Meaning                                  |
|-----------------|-------------------------------------------------------------------------|------------------------------------------|
| **Imperative**  | Old-style taxi: "turn right on B, left on C, left, then right on D, stop" | Specify **what** to do **and how**       |
| **Declarative** | Uber: "drive to Tom's house"                                            | Specify **what** you want; the system figures out **how** |

## 2. Infrastructure as Code Example 🏗️

**Imperative:** step-by-step instructions.

1. Provision a VM named `web-server`
2. Install Nginx
3. Edit the config to use port 8080 and set the path to web files
4. Download the source code from Git
5. Start Nginx

**Declarative:** just declare the requirement: a VM named `web-server` with Nginx, port 8080, web file path, and source code location. The system does everything needed to get there.

Declarative tools: **Ansible, Puppet, Chef, Terraform**.

### Problems with the imperative approach

- What if only **half the steps** ran the first time and you run the instructions again?
- You need extra **checks**: does the VM `web-server` already exist? Fail, or continue? Same for creating a database or importing data.
- Upgrading Nginx to 1.18 should be as simple as changing the version in the config. A declarative system knows what's already done and applies **only the necessary changes**.

## 3. Imperative Approach in Kubernetes ⚙️

There are two flavours.

### a) Imperative commands

| Command                    | Purpose                              |
|----------------------------|--------------------------------------|
| `kubectl run`              | Create a pod                         |
| `kubectl create deployment`| Create a deployment                  |
| `kubectl expose`           | Create a service to expose something |
| `kubectl edit`             | Edit an existing object              |
| `kubectl scale`            | Scale a deployment / replica set     |
| `kubectl set image`        | Update the image of a deployment     |

Example syntax:

```bash
kubectl run nginx --image=nginx
kubectl create deployment nginx --image=nginx
kubectl expose deployment nginx --port=80
kubectl scale deployment nginx --replicas=5
kubectl set image deployment nginx nginx=nginx:1.18
```

✅ **Pros:** quick, no YAML needed, **very helpful in the certification exam**.

❌ **Cons:**

- Limited functionality; advanced cases (e.g. a multi-container pod) need long, complex commands.
- Run once and **forgotten**. They only exist in that user's shell history, so others can't tell how the object was created.
- Hard to track in large or complex environments.

### b) Imperative with object configuration files

Write a YAML manifest and use `create`, `replace`, `delete`:

```bash
kubectl create -f pod.yaml      # Create
kubectl replace -f pod.yaml     # Update (object must already exist)
kubectl delete -f pod.yaml      # Delete
```

✅ The YAML is always available and can be stored in **Git**, with a **review and approval process** before changes reach production.

### Changing an object: `edit` vs `replace`

| Method            | What happens                                                                                           | Caveat                                                                                       |
|-------------------|--------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| `kubectl edit <obj>` | Opens the **live** definition from Kubernetes memory (includes extra `status` fields). Save & quit applies the change | The change is **not recorded** in your local file. A teammate applying the old file later **loses your change** |
| Edit local file + `kubectl replace -f` | Change is made in the file, then applied                                               | Change is **tracked** in Git / review process ✅ (preferred)                                  |

Use `kubectl edit` only when you're sure you won't rely on the local config file later.

To completely delete and recreate an object:

```bash
kubectl replace --force -f pod.yaml
```

### Why imperative is "taxing" for the admin 😓

- `create` on an object that **already exists** → error: *already exists*.
- `replace` on an object that **doesn't exist** → error.
- You must always know the current state and check before acting.

## 4. Declarative Approach in Kubernetes 🎯

Use the **same object config files**, but manage everything with `kubectl apply`:

```bash
kubectl apply -f pod.yaml        # single file
kubectl apply -f ./manifests/    # whole directory: all objects at once
```

- `apply` **creates** the object if it doesn't exist.
- If it exists, `apply` **updates only what changed**.
- It never throws *already exists* or *cannot update* errors; it figures out the right action.
- To make changes: update your local files (change an image, edit fields, add new files) and run `apply` again.

## 5. How `kubectl apply` Works Internally 🔍

`apply` compares **three** things before deciding what to change:

| # | What                              | Where it lives                                                        |
|---|-----------------------------------|-----------------------------------------------------------------------|
| 1 | **Local configuration file**      | Your machine (YAML)                                                   |
| 2 | **Live object configuration**     | Kubernetes cluster (similar to your file, plus extra `status` fields) |
| 3 | **Last applied configuration**    | Stored **inside the live object** as an annotation (JSON format)      |

### Flow

1. **Object doesn't exist** → it's created. Kubernetes stores the live config. Because `apply` was used, your YAML is also converted to **JSON** and stored as the **last applied configuration**.
2. **Object exists and you change a value** (e.g. `nginx` image → `1.19`): the local value is compared with the live value. If different, the **live config is updated**, and the last applied JSON is **updated to the latest**.

### Why do we need the last applied configuration?

It tells `apply` which fields were **removed** from the local file.

| Field is in...                                        | Result                                                                 |
|-------------------------------------------------------|------------------------------------------------------------------------|
| Local file, but value differs from live               | Live is **updated** with the local value                               |
| **Last applied** but **not in local** file            | Field was deleted by you → **removed from live config**                |
| **Live** only (not in local, not in last applied)     | Left **as is**                                                         |

Example: a `type` label existed when you last ran `apply`, but you deleted it from the local file. Next `apply` sees it in the last applied config but not in the local file, so it removes it from the live object.

### Where is it stored?

On the live object as an annotation:

```
kubectl.kubernetes.io/last-applied-configuration
```

⚠️ This is stored **only when you use `apply`**. `create` and `replace` do **not** store it.

🚫 **Don't mix imperative and declarative approaches** on the same objects. Once you use `apply`, stick with `apply`.

## 6. Exam Tips 📝

| Situation                                                                                   | Best approach                                        |
|---------------------------------------------------------------------------------------------|------------------------------------------------------|
| Just create a pod or deployment with a given image                                           | **Imperative command** (`run`, `create deployment`)  |
| Edit one property of an existing object                                                      | `kubectl edit` (quickest)                            |
| Complex requirement (multiple containers, env variables, commands, init containers, etc.)    | **YAML file** + `kubectl apply -f`                   |

- With a YAML file, if you make a mistake you can just fix the file and `apply` again.
- Practice the **imperative commands** to save time in the exam, and get familiar with the Kubernetes documentation pages.

## 🚀 Summary Cheat Sheet

| Command                              | Approach     | Purpose                                      |
|--------------------------------------|--------------|----------------------------------------------|
| `kubectl run` / `create deployment` / `expose` | Imperative | Quickly create objects                  |
| `kubectl edit` / `scale` / `set image`         | Imperative | Quickly modify objects                  |
| `kubectl create -f`                  | Imperative   | Create from file (fails if it exists)        |
| `kubectl replace -f`                 | Imperative   | Update from file (fails if it doesn't exist) |
| `kubectl replace --force -f`         | Imperative   | Delete and recreate                          |
| `kubectl delete -f`                  | Imperative   | Delete from file                             |
| `kubectl apply -f <file or dir>`     | **Declarative** | Create or update as needed                |

- **Imperative** = what + how. **Declarative** = just the desired end state.
- `kubectl edit` changes only the **live** object, so your local file becomes out of date.
- `apply` compares **local file + live config + last applied config**.
- Last applied config is stored as an **annotation** on the live object, **only by `apply`**.
- Never mix `create`/`replace` with `apply` on the same objects.
- Exam: imperative commands for speed, YAML + `apply` for complex objects.
